## AXE 4 — SÉCURITÉ

### 🔴 CRITIQUE — Secrets réels commités dans git
`backend/.env.CLEAN` est **suivi par git** (présent dans l'historique, commits `662155b`, `763d88e`, poussé sur GitHub) et contient de **vraies valeurs** :
- `SUPABASE_JWT_SECRET` — secret de signature des tokens.
- `CLOUDINARY_API_SECRET`, `CLOUDINARY_API_KEY`, `CLOUDINARY_URL`.
- `DATABASE_URL` (avec mot de passe PostgreSQL).

Le `.gitignore` liste bien `backend/.env.CLEAN` (ligne 84) **mais trop tard** : un fichier déjà commité n'est pas dé-suivi par `.gitignore`.

**Aggravation :** `auth.middleware.js` accepte les tokens **HS256 signés avec `SUPABASE_JWT_SECRET`**. Quiconque a lu ce fichier peut **forger un token valide, y compris rôle ADMIN**, et accéder à toute la base.

**Actions requises (dans cet ordre) :**
1. **Faire tourner (rotate) TOUS les secrets exposés** : Supabase JWT secret, Cloudinary (régénérer API secret), mot de passe PostgreSQL/DATABASE_URL. → À faire dans les dashboards Supabase / Cloudinary / Supabase DB. **C'est l'action pilote la plus urgente.**
2. `git rm --cached backend/.env.CLEAN` puis commit (arrête le suivi ; le `.gitignore` prend alors effet).
3. Idéalement : purger le fichier de l'historique git (`git filter-repo` ou équivalent) — les anciens commits contiennent encore les valeurs même après suppression.

### 🟢 Points sains à préserver
- **`workspaceGuard`** : vérifie l'appartenance de l'utilisateur au workspace en base avant tout accès. Isolation multi-tenant correcte.
- **Scoping contrôleurs** : `exercice.controller.js` propage `req.workspaceId` à chaque appel service (get/create/update/delete). Pas de fuite inter-workspace au niveau contrôleur.
- **`baseMutationGuard`** : la BASE n'est modifiable que par un ADMIN plateforme.
- **helmet + CSP renforcée**, **CORS en allowlist** (exacts + localhost + domaines Vercel), **rate limiting** lecture + écriture, **redaction** des en-têtes sensibles dans les logs (pino), **dev bypass** verrouillé (exige `NODE_ENV=development` ET `DEV_BYPASS_AUTH=true`).

### 🟡 Points mineurs
- **Incohérence avec une décision figée** : la doc dit « RS256 via JWKS uniquement », mais le code accepte HS256 **et** RS256 (+ une branche « algorithme inconnu » qui tente les deux). À clarifier : soit c'est voulu (tokens Supabase legacy HS256) et on met à jour la décision figée, soit on restreint à RS256.
- **Fallback DB transitoire** : en cas de DB injoignable, les GET non-admin sont autorisés avec un rôle **issu du token** (pas de la base). Risque faible (admin exclu, lecture seule) mais à connaître.
- `frontend/environment.prod.ts` expose `supabaseKey` = **clé anon** : c'est **normal** (clé publique par design), **pas** une fuite.
